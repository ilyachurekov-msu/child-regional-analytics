# Общий платформенный профиль

Использован существующий пакет shared-contracts 1.0.0, справочник регионов не перенумеровывался. Read-only проверены media/codex/mvp-acceptance: после migration0003 там используются те же цифровые RU-* ключи; темы верхнего уровня совпадают. Исторические 83 ISO-кода media сопоставлены числовым ключам. Practices/контракт по указанному имени недоступен (404); это не доказательство отсутствия проекта.

В пакет добавлены topics.csv, identity.py и source.schema.json. Канонический UUIDv5 соответствует уже реализованной процедуре media: namespace 72c4db98-6752-5fe0-a56d-af600628f13b, строка source:<lowercase type>:<normalized URL>. Сохраняются scheme, www и значимые query; удаляются fragment и tracking-параметры; hostname/IDNA и default ports нормализуются. source_type является частью идентификатора. Типы core-сущностей остаются UUID/string/date/timestamptz согласно схеме; дополнительное normalized_identifier — локальное поле legacy regional API, не обязательное общее поле.

Legacy source_uuid(normalized_identifier) сохранен в пакете для обратной совместимости. Миграция regional0003 создает regional.source_aliases и заполняет canonical→legacy для существующих источников, не меняя PK core.sources, наблюдения и ревизии. Коллизия canonical ID останавливает миграцию, а не объединяет строки. Новые импорты также регистрируют alias. scripts.export_source_mapping выводит проверяемую таблицу соответствий без изменения БД. Потребители интеграции должны использовать canonical ID из alias, а не заменять PK старых строк.

План: backup → dry-run таблицы соответствий → проверка коллизий → миграция aliases → сверка числа наблюдений/истории → подключение адаптеров соседних модулей отдельными согласованными PR. Откат 0003 удаляет только таблицу aliases. Изменений в media/practices не выполнялось.

Migration0004 корректирует только локальное поддерживаемое временное покрытие RU-42 с 2018-11-03 на 2018-01-01: исходный официальный ежегодник содержит полный 2018 год. Это не дата основания субъекта. Идентификатор не меняется. При CORE_MANAGED_EXTERNALLY=true справочник не изменяется: владелец платформы должен отдельно согласовать покрытие. Downgrade не разрешает вернуть старую дату, если уже сохранены наблюдения раннего периода. Соседние копии метаданных сами не исправлялись, поэтому совпадение всех полей трех модулей не заявлено.

Версионирование: стабильные ID не переиспользуются; добавление необязательных полей — minor, удаление/смена значений/семантики или namespace — major с crosswalk и переходным периодом. Текущий пакет является техническим кандидатом; PLATFORM_AGREED=false. Полное согласование трех модулей не заявляется. Legacy platform.schema.json сохранена для совместимости; source.schema.json описывает общий канонический профиль без локальных полей.


## Аддитивный кандидат 1.1.0: профиль 89

Все 85 ранее существовавших ID субъектов сохранены. Добавлены RU-80/81/84/85 с названиями из профиля DataLens; это прикладные цифровые ключи, не коды ISO 3166-2. Начало поддерживаемого годового покрытия — 2023-01-01, федеральный округ неизвестен (пустая строка), ОКАТО/ОКТМО не выдумываются. Candidate package, API health и JSON Schema используют согласованную версию 1.1.0; прежний профиль 1.0.0 остается исторической основой. PLATFORM_AGREED=false.

Migration0005 добавляет четыре строки только при локальном управлении core, ON CONFLICT DO NOTHING сохраняет существующие операторские записи. Downgrade не удаляет справочные ID: они могут уже использоваться потребителями либо существовать до миграции. При внешнем управлении core владелец должен принять аддитивное расширение отдельно; соседние репозитории не менялись. План принятия: сверка всех 89 names/IDs → проверка временного покрытия → локальная миграция → отдельные согласованные изменения потребителей.
