# Техническое задание для Codex
## Проект 1. Региональная аналитика

### 1. Твоя роль

Ты выступаешь как senior Python-разработчик, архитектор баз данных, Data Engineer и BI-аналитик.

Твоя задача — разработать с нуля самостоятельное веб-приложение «Региональная аналитика», предназначенное для мониторинга социально-демографического положения детей и семей в субъектах Российской Федерации.

Работай как инженер полноценного программного продукта, а не как автор учебного прототипа.

Проект должен иметь понятную структуру, документацию, тесты, автоматическую загрузку данных и возможность последующего подключения к общей аналитической платформе.

### 2. Общая архитектура и совместимость

Этот проект — один из трех независимых модулей будущей платформы «Навигатор детства».

Другие модули:
- `child-media-monitor` — мониторинг информационного поля.
- `child-practices-search` — поиск социальных практик.

Эти проекты разрабатываются независимо, в других репозиториях. Не пытайся реализовать их функциональность.

Требования к совместимости:

- Python 3.11+.
- PostgreSQL 16.
- Расширение pgvector должно поддерживаться инфраструктурой, но данному модулю векторный поиск не требуется.
- FastAPI для REST API.
- Streamlit для самостоятельного MVP-интерфейса.
- SQLAlchemy 2.x и Alembic.
- Docker и Docker Compose.
- Pydantic для схем данных и конфигурации.
- Все API начинаются с `/api/v1/`.
- Все даты обмена — ISO 8601; временные метки хранятся в UTC.
- Все сущности используют стабильные UUID, за исключением естественных идентификаторов справочников.
- Код должен работать локально на Windows с использованием Docker Desktop.

Используй PostgreSQL-схемы:
- `core` — общие справочники, определенные ниже.
- `regional` — собственные таблицы модуля.

Не создавай таблицы в схемах `media` и `practices`.

Все изменения структуры собственных таблиц оформляй миграциями Alembic.

### 3. Общий контракт платформы

Обязательно реализуй совместимость со следующими сущностями.

**core.regions**
- `region_id` — стабильный внутренний идентификатор региона (TEXT, первичный ключ).
- `name` — название.
- `federal_district` — федеральный округ.
- `okato_code` — код ОКАТО, допускает NULL.
- `oktmo_code` — код ОКТМО, допускает NULL.
- `valid_from` — дата начала действия записи.
- `valid_to` — дата окончания действия записи, допускает NULL.

`region_id` должен быть одинаковым во всех трех проектах. Используй версионируемый файл `contracts/regions.csv` с явно заданными идентификаторами. Не генерируй их случайным образом и не используй название региона в качестве ключа.

**core.topics**
- `topic_id` — стабильный строковый код.
- `name` — наименование.
- `parent_topic_id` — родительская тема или NULL.

Начальный классификатор:
- `demography` — демография;
- `family` — семья;
- `education` — образование;
- `healthcare` — здравоохранение;
- `social_support` — социальная поддержка;
- `orphanhood` — сиротство и семейное устройство;
- `safety` — безопасность;
- `infrastructure` — инфраструктура.

**core.sources**
- `source_id` — UUID;
- `source_type` — тип источника;
- `name` — название;
- `url` — URL или NULL;
- `publisher` — издатель/организация или NULL;
- `created_at` — дата регистрации.

Обеспечь уникальность нормализованного идентификатора источника, чтобы разные модули не создавали его дубликаты при объединении.

Общие справочники хранятся в схеме `core`, но модуль не должен владеть их изменениями после интеграции. При локальном запуске используй версионируемые seed-файлы, а не самостоятельную несовместимую структуру.

Подготовь `contracts/` с JSON Schema или OpenAPI-описанием общих сущностей и фиксированным номером версии `1.0.0`.

### 4. Цель продукта

Разработать интерактивную систему анализа положения детей и семей в субъектах РФ.

Пользователь должен иметь возможность:
1. Выбрать регион.
2. Открыть его статистический профиль.
3. Посмотреть значения ключевых показателей.
4. Изучить динамику за несколько лет.
5. Сравнить регион с федеральным округом и Россией.
6. Найти регионы с наиболее неблагоприятными значениями или динамикой показателей.
7. Сформировать краткую аналитическую справку.
8. Экспортировать данные в Excel или CSV.

### 5. Источники информации

Приоритетно использовать открытые данные:
- Росстата;
- ЕМИСС;
- Минпросвещения;
- Минздрава;
- Минтруда;
- других официальных источников при наличии подходящих наборов данных.

Не выдумывай API и адреса выгрузки.

Сначала проверь доступность источников, условия использования, структуру опубликованных данных и способы загрузки.

Если автоматизированный доступ невозможен, создай загрузчик файлов CSV/XLSX и задокументируй ручной порядок получения данных.

Запрещается подменять недоступные реальные значения вымышленными. Демонстрационные данные допускаются только в отдельном режиме, с явно заметной маркировкой.

### 6. Структура базы данных

В схеме `regional` создай как минимум следующие таблицы.

**indicators**
- `indicator_id` UUID;
- `code` TEXT UNIQUE;
- `name` TEXT;
- `description` TEXT;
- `topic_id` TEXT;
- `unit` TEXT;
- `direction` TEXT — рост показателя считается положительным, отрицательным или неоднозначным;
- `methodology` TEXT;
- `is_active` BOOLEAN.

**indicator_values**
- `value_id` UUID;
- `indicator_id` UUID;
- `region_id` TEXT;
- `period_start` DATE;
- `period_end` DATE;
- `value` NUMERIC;
- `source_id` UUID;
- `published_at` TIMESTAMPTZ;
- `loaded_at` TIMESTAMPTZ;
- `data_status` TEXT;
- `is_current` BOOLEAN;
- `revision_number` INTEGER.

**import_batches**
- идентификатор загрузки;
- источник;
- дата загрузки;
- контрольная сумма файла;
- число обработанных строк;
- число ошибок;
- статус выполнения.

**data_quality_issues**
- идентификатор проблемы;
- связанная загрузка;
- показатель;
- регион;
- тип ошибки;
- описание;
- статус исправления.

Добавь необходимые индексы и ограничения.

Уникальность наблюдения должна учитывать показатель, регион, период и версию данных.

Повторная загрузка того же файла не должна создавать дубликаты. Исправленные публикации источника должны сохранять историю изменений.

### 7. Первоначальные показатели

Начни с компактного набора показателей, действительно доступных в официальной статистике.

Приоритетные группы:
- численность населения;
- численность населения детских возрастов;
- рождаемость;
- смертность;
- браки и разводы;
- показатели семейного устройства детей;
- отдельные показатели образования;
- отдельные показатели здравоохранения;
- показатели социальной поддержки семей.

Для каждого показателя должны быть известны:
- точное определение;
- единица измерения;
- периодичность;
- первичный источник;
- метод расчета, если показатель производный;
- ограничения сопоставимости между регионами и годами.

Не включай показатель в рабочую витрину, пока не получена методологически понятная информация.

### 8. ETL-процесс

Реализуй следующий конвейер:

Получение файла → проверка формата → сохранение исходной версии → нормализация → сопоставление регионов → проверка типов → контроль пропусков → сохранение в БД → запись отчета о загрузке.

Требования:
- поддержка CSV, XLSX и JSON, когда формат реально используется источником;
- автоматическое сопоставление названий регионов со справочником;
- отдельная очередь для неоднозначных названий;
- защита от дублирования;
- журнал ошибок;
- повторяемые операции;
- возможность пересчитать витрины;
- тесты на некорректные значения.

Не превращай отсутствующие значения в нули.

Не объединяй показатели с разными определениями без документированной процедуры гармонизации.

### 9. Аналитические возможности

Реализуй:

**Паспорт региона**
- основные демографические показатели;
- показатели семейного благополучия;
- сравнение с РФ;
- сравнение с федеральным округом;
- динамика;
- ссылки на первичные источники.

**Сравнение регионов**
- выбор 2–5 регионов;
- таблица показателей;
- графики;
- абсолютные и относительные изменения.

**Карта**
- выбор показателя и года;
- визуализация значений;
- отображение отсутствующих данных отдельным цветом;
- всплывающие карточки региона.

**Анализ отклонений**
- выявление наиболее существенных изменений;
- сравнение с медианой субъектов;
- сравнение с уровнем РФ;
- расчет нормированных значений там, где он методологически допустим.

**Индекс благополучия**
Не вводи единый интегральный индекс автоматически.

Сначала реализуй прозрачный конструктор индекса с выбором показателей, направлений нормирования и весов.

По умолчанию показывай отдельные показатели и группы, поскольку объединение разных измерений благополучия требует обоснования.

### 10. Пользовательский интерфейс

Разработай Streamlit-приложение со страницами:

1. Главная — обзор системы.
2. Карта России.
3. Паспорт региона.
4. Сравнение регионов.
5. Динамика показателей.
6. Качество и актуальность данных.
7. Экспорт аналитической справки.

Интерфейс на русском языке.

Стиль — строгий аналитический, без лишней декоративности.

На каждом графике должны отображаться источник, период наблюдения и единица измерения.

### 11. REST API

Реализуй как минимум:

- `GET /api/v1/regions`
- `GET /api/v1/regions/{region_id}`
- `GET /api/v1/regional/indicators`
- `GET /api/v1/regional/values`
- `GET /api/v1/regional/profiles/{region_id}`
- `GET /api/v1/regional/comparison`
- `GET /api/v1/regional/data-quality`

Фильтры, пагинация, валидация и стандартизированные ошибки обязательны.

OpenAPI должен генерироваться автоматически.

### 12. Требования к интеграции

В будущем к паспорту региона будут добавлены:
- публикации и общественные инфоповоды из модуля `media`;
- социальные практики из модуля `practices`.

Не реализуй эти источники сейчас.

Вместо этого подготовь документ `docs/integration.md`, где укажи:
- как другие модули будут использовать `region_id`;
- какие API предоставляет твой модуль;
- какие данные передаются при интеграции;
- ограничения совместимости;
- версию общего контракта.

Не создавай внешние ключи на таблицы других модулей.

### 13. Безопасность

Используй только открытые публичные данные.

Не применяй реальные закрытые ведомственные файлы, персональные данные детей, сведения об обращениях граждан или служебные материалы.

Секреты — только через переменные окружения. `.env` не должен попадать в Git.

Поддержи автономную работу аналитического интерфейса и базы после импорта данных.

### 16. Критерии готовности MVP

MVP считается готовым, когда:
- приложение запускается локально через Docker Compose;
- загружены реальные данные хотя бы по 5 сопоставимым показателям;
- поддерживается выбор субъектов РФ;
- работает сравнение как минимум двух регионов;
- отображаются динамика и источники;
- повторная загрузка не создает дубликатов;
- API покрыт основными тестами;
- реализован экспорт;
- имеется полная инструкция запуска;
- интеграционный контракт документирован.

В конце подготовь отчет с описанием реализованных функций, архитектуры, тестов, ограничений и следующего этапа разработки.
